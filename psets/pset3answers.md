## Changes to the design document
### Part B
1. We neglected to mention that `fork()` should also increment the `refcount` of each copied `vnode`. We also forgot about `exit()`; it will need to walk through the process' `fdtable` and close everything. (When we get to multithreading, only the last thread should do this.)
2. At the time of design we did not think about process VFS cleanup upon exit. `syscall_exit()` must walk through the `proc::fdtable[]` and close all open file descriptors in the same way `syscall_close()` does it.
3. The `kb_c_vnode` does not require a pointer to the keyboard and console states as the document stated, as they are global singletons.
4. In case it was not clear to the reader from the design document, the only functions that can possibly block are the various `read()` and `write()` functions from `vnode` derived classes. In our case, currently only pipe buffer read/writes actually block if buffer is empty/full.
5. The computations for read and write size for `memfile` writing were incorrect; at the time we were not aware of `memfile::set_length()`. The new method is to check `memfile::len_ - vnode::offset_` and if it is smaller than `sz`, try to set the length and if it fails just return the error without doing anything (for writes---for reads, just read as much as possible). There are two possible designs about how to do the write; we followed the one given by a TF during OH.
6. **Locking strategy**: Ours is relatively fine-grained but does not appear to have any races or deadlocks. We have carefully thought through the system and discuss it in parts C and D below. **Note**: we did not mention in the design document that `refcount` must be updated atomically; ultimately we chose to implement this by making a lock just for `refcount` called `open_close_lock_` defined in `vnode` and inherited by all types of `vnode`s. The purpose of this lock is entirely to make refcounts atomic and we could have equivalently just made `refcount_` atomic. We chose not to do this since the lock allowed for more accurate assert statements and prints for debugging, and it makes the logic of the code more clear. No other locks are used in `vnode`; when we go to multithreading, the only change we will need is to lock accesses to the threads' shared `fdtable` which does not require action at the `vnode`/VFS level. The locks in `kb_c_vnode` are just the old locks from the driver `syscall_read/write()` code.
7. The only change to future work is the parenthetical note from bullet point (1).

### Part C
The bounded buffer implementation follows closely the implementation from CS 61 linked on the problem set statement; as such, we refrain from restating all of the logic for the bounded buffer. We built the pipe `vnode` system in our design document early on, so any updates are below.
1. In the document it was decreed that the writer pipe `vnode` should allocate and free the buffer. It turns out the natural way is slightly more complicated. We added two additional boolean metadata to the bounded buffer: `read_closed` and `write_closed`. The constructor of the `write` class shall as defined in the design document allocate the bounded buffer, but the destructor shall only free the buffer if both of the above booleans are true. The destructor for the write end shall, all under the shared bounded-buffer lock, set `write_closed` to true, then check if the dual `read_closed` is true, freeing `bbuf` if so. Otherwise, it will just exit. The read end destructor does the same, switching the bools above.
2. In the document we declared that the `close` syscall would call `kfree()`. Since we need destructors to be called, `delete` will be used instead. Due to the specifications of the C++ linker, the destructor of the base `vnode` struct is declared as virtual and all virtual functions in the base struct are subsequently defined, as the struct is no longer pure virtual.
3. **Locking strategy**: we define two locks here. The first lock is the basic `vnode` lock that every `vnode` inheriter shares--the `open_close_lock_`. The second lock is that of the bounded buffer, `bbuf_->lock_`, shared between the two pipe `vnode`s. Any I/O to the pipe is done through this lock. Since actions corresponding to the two locks are entirely disjoint, there are no deadlocks. 

### Part D
Updates to the design:
1. Validation of the filename string is a priori ambiguous because the size of the string isn't passed explicitly. If the user gives a gigantic string that has no end (probably on accident by passing in a pointer to unintended chunks of memory) we should fail. As such we set the maximum filename size to `MAX_FILENAME_LEN = 64` in `kernel.hh` to match that of `memfile::namesize`. We then compute the size by walking through the string until we find the null terminator or if we determine the string is too long. Given a size from there, we can call the I/O validator from Part A to finish validation.
2. It is important to reiterate that many `memfile_vnodes` can point to the same `memfile`, due to the locking strategy below.
3. **Locking strategy**: we have two locks in `memfile`. The first is a global lock on `initfs` that locks the static function `initfs_lookup()` in its entirety. This prevents the table from being raced on. The second is a per-`memfile` lock that `memfile_vnode`s use to serialize reads and writes to a file. Since these two functions are completely disjoint, they do not deadlock. In addition, we have the standard `open_close_lock` inherited from `vnode` as discussed in part B. All `vnode` offset are modified under lock (except `pipe_vnode` which doesn't use `offset_`).

2. Built a Unix Domain Socket: the design of the UDS is outlined in `k-vfs.hh` at the bottom and all definitions are made  in `k-vfs.cc`. The basic idea is that a UDS consists of a client and server pointer, and metrics about its status. There is a global array of `NSOCK=8` `uds*` pointers defined in `kernel.cc`, and a server process call to `syscall_socket(char* name)` will allocate a new UDS after validating `name` the same way `open` validates names (via a helper function `pathname_invalid()`). No client may connect to it until the server has called `syscall_listen()`. Client `connect()` and server `accept()` both block while waiting for the counterpart. In our design every UDS consists of one client and one server process, and no other process may connect to a socket when both are filled. To be as telecom-practical and fancy as possible, we generated a *timeout* of `UDS_TIMEOUT=100` msecs in the blocking, so that after this time the call returns saying nothing was found. If everything goes well (and we implement a lot of checks--take a look at `uds::read()` and `uds::write()`), the client can send a file descriptor, which `syscall_sendfd()` will verify is valid, and then the server can read it by `syscall_receivefd()`. The latter calls `uds::read()` which if a valid fd is available, will grab the corresponding `vnode*` pointer and try to set it on the server `fdtable` to the same `fd`, but if that is taken assign it to the first available `fdtable` and return it; or return `E_MFILE` if server has too many open files. We wrote an automated and fairly comprehensive test for UDS, to run it use `make run-uds`. (I spent a long time on this so I hope you like it :D).
